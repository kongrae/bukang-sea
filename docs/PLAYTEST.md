# 실제 이용자 플레이테스트

2026-09-30 개선 작업 5번. 현재 게임 빌드 `988a9c8a61d5`를 대상으로 시험 절차·기록 양식·분석 도구를 준비했다. **실제 이용자 결과는 아직 미수집이며, 재미·체감 난이도·출시 가능 여부를 확정하지 않았다.**

## 준비물과 실행

- 기록: [RECORDS.xlsx](playtest/RECORDS.xlsx). '시도 기록'은 시도마다 한 행, '설문'은 이용자/빌드/세션마다 한 행이다. '안내'에 모든 필드 정의와 빌드 ID가 있다. 실제 결과 예시를 채우지 않았다.
- 현재 결과: [RESULTS.md](playtest/RESULTS.md). 실제 기록 0명으로 표시하며, 자동 검증 수치를 사람의 결과로 대신 넣지 않는다.
- 초보 5명으로 첫 파일럿을 진행한다. Android 3명·iPhone 2명을 목표로 하고, 기기 모델·브라우저 버전·화면 잘림은 notes에 기록한다. 인원을 충족하지 못하면 실제 인원만 보고한다. 설문 응답은 익명 ID만 사용한다.
- 후반 검증은 코어 세션과 별도로 진행한다. 경험자 3명부터 장치 이해·복합 수로의 문제를 찾되, 초보 결과와 합치지 않는다. 같은 사람이 두 기기를 쓰면 기기별 ID를 다르게 부여한다.

```powershell
npm run build:playtest
npm run serve:playtest
# 휴대폰이 같은 Wi-Fi라면 별도 터미널에서 다음 명령 사용
node tools/serve.js playtest 5175 --host
```

PC: `http://127.0.0.1:5175/?tester=P01`. 휴대폰: `http://<PC의 IPv4>:5175/?tester=P01`. 실제 기기에서 접속 가능 여부를 먼저 확인한다. HTTP LAN 시험은 PWA 설치·오프라인 캐시·네이티브 앱 시험을 대신하지 않는다.

기본 URL은 정상적인 수로 개방 순서를 유지한다. 진행자는 후반 세션에서만 `&all=1`을 붙인다. 예: `http://<PC의 IPv4>:5175/?tester=P01&all=1`. 이때만 모든 수로를 바로 고를 수 있다. 화면에는 PLAYTEST/TEST가 표시된다. 기록은 이용자·빌드·core/lab별로 분리되고 정식 저장 키를 사용하지 않는다. 새 이용자는 새 ID로 시작하고, 같은 ID의 재접속은 복원 시험에 사용한다. 처음부터 다시 관찰하려면 `P01_retry`처럼 새 ID를 부여하고 이전 ID와의 관계를 notes에 적는다.

테스트 빌드는 `playtest/`에 생성되며 배포 결과물·Capacitor webDir에 포함되지 않는다. 서비스 워커를 등록하지 않고 폰트는 로컬에서 읽는다. 입력·맵·별 판정·힌트·장치 안내·저장 로직은 현재 게임 그대로다. `all=1`은 후반 접근을 위한 차이이므로 자연 진행/이탈률을 평가할 때 사용하지 않는다.

## 코어 세션: 1–12번 자연 진행

총 40분: 플레이 최대 30분, 복원 시험 5분, 설문 5분. 진행자는 해결 방향을 알려주지 않는다.

1. 새 ID로 접속하고 “상어를 바다로 보내 보세요. 화면에 보이는 기능은 자유롭게 사용하세요.”라고만 말한다. 첫 조작까지의 시간과 처음 잘못 이해한 점을 notes에 기록한다.
2. 1번부터 '다음 수로'로 자연 진행한다. 숭어 수집·별 3개는 이용자가 선택하게 한다. 첫 시도의 별 3개 비율은 수집 동기의 관찰치이며, 이 세션만으로 별 기준이 쉽거나 어렵다고 판정하지 않는다.
3. 수로 진입 안내를 닫고 조작할 수 있을 때부터 시간을 잰다. 연습/일반 한 시도는 최대 180초, 도전은 최대 300초다. 전체 30분 한도에 도달하면 현재 시도는 timeout, 아직 시작하지 않은 수로는 not_run으로 기록한다.
4. '처음부터'는 새 시도 번호다. 되돌리기는 같은 시도다. 클리어·자발적 포기·시간 초과·기능 오류로 시도를 끝내면 즉시 한 행을 작성한다. 클리어한 시도만 골라 적지 않는다.
5. 숭어를 건너뛴 탈출, 그물 재사용을 알아챈 시점, 구조정이 움직이는 순서를 잘못 예상한 위치를 notes에 기록한다. 중간에 테스트를 그만두면 이유를 그대로 적고 미도달 수로와 실제로 시도한 포기를 구분한다.

| 수로 | 핵심 관찰 |
| --- | --- |
| 1–2 | 막힐 때까지 이동한다는 규칙, 첫 스와이프, 작은 화면 오조작 |
| 3–5 | 숭어와 별 조건 이해, 수집을 위해 다시 시도하는지 |
| 6 | 구조정 안내와 '상어 다음 구조정' 순서 이해 |
| 7–8 | 고정 화살표 방향 인지, 물줄기 경로 예측 |
| 9 | 첫 도전에서 막히는 이유와 포기 여부 |
| 10–11 | 그물 탭·회수·무료 재사용 이해, 힌트 안내의 실행 가능성 |
| 12 | 두 그물·구조정·숭어가 함께 있는 판의 가독성과 부담 |

## 복원과 조작 시험

12번을 아직 시작하지 않았으면 core 결과 기록을 마친 뒤 별도 lab URL로 들어가 진행자가 12번을 골라준다. 이 보충 시험 결과를 코어 첫 시도에 섞지 않는다.

- 그물을 설치하고 유효한 이동을 한 뒤, 현재 판과 HUD를 사진으로 남긴다. 브라우저 새로고침 → 이어 하기 → 상어·숭어·그물·구조정·이동 수를 비교한다. 되돌리기로 한 단계 이전 상태도 확인한다.
- 앱 전환 후 복귀, 목록으로 나갔다 이어 하기, '처음부터' 후 재접속을 각각 확인한다. 네이티브 APK가 있으면 별도 네이티브 세션으로 앱 전환·강제 종료도 시험하고 notes에 실행 환경을 명시한다.
- 스토리와 오늘의 수로를 각각 진행한 뒤 서로 유지되는지 확인한다. 별/스킨의 기존 기록도 비교한다. 한 항목이라도 달라지면 설문의 resume는 fail, 모두 확인하면 pass, 미실시면 not_run이다.
- 짧은 터치와 의도한 스와이프를 구분해 관찰한다. 막힌 방향으로 정상 입력한 것을 오조작으로 세지 않는다. 의도가 불명확하면 misinputs를 비워 두고 발언을 적는다.

## 기록과 분석

기록에는 게임 빌드 `988a9c8a61d5`, core/lab, 경험 new/experienced, 실제 기기 android/iphone/desktop을 넣는다. 브라우저의 모바일 크기 에뮬레이션은 desktop이다. duration_sec는 실제 초, clear는 moves/stars 필수, 미클리어 stars는 빈칸이다. 기능 오류는 blocked로 기록하고 재현 절차를 남긴다. 관찰 불가·무응답은 빈칸이며 확인한 '사용 없음'만 0이다. 진행자가 경로를 알려주면 assisted=1이다.

'시도 기록'과 '설문'을 각각 **CSV UTF-8**로 저장한다. 숫자를 문자열 등급이나 임의의 점수로 바꾸지 않는다. 데이터가 입력 범위를 넘으면 표를 확장한다. 분석 도구는 표 크기에 제한이 없고 빈 행을 무시한다.

```powershell
npm run playtest:report -- attempts.csv survey.csv --out results.md
# 설문 없이 시도만 분석 가능
npm run playtest:report -- attempts.csv --out results.md
# 결과가 아직 없을 때의 상태 보고서
npm run playtest:report -- --out docs/playtest/RESULTS.md
```

분석은 빌드·세션·경험·기기·수로별 첫 시도를 집계한다. 재도전, 미실시, 포기, 시간 초과, 기능 막힘을 구분하고 모든 비율에 분자/분모를 표시한다. 힌트·오조작·진행자 도움이 빈칸이면 그 지표의 분모에서도 제외한다. 클리어 시간 중앙값은 성공한 첫 시도만의 값이므로 포기/초과가 많은 판을 빠른 판으로 해석하지 않는다. 다른 빌드는 별도 그룹이며 이전 맵의 이름을 현재 이름으로 추정하지 않는다.

처음에는 아래를 **재검토 신호**로 사용한다. 출시 합격 기준이나 검증된 업계 표준은 아니다.

- 저장 복원·진행 기록 손실·입력 멈춤이 한 번이라도 재현되면 기능 원인을 먼저 수정한다.
- 첫 장치의 행동을 같은 이유로 2명 이상 잘못 예상하면 장치 그림·안내·도입 맵을 함께 검토한다.
- 코어 수로를 실제로 시작한 초보 관찰이 5건 이상이고 그중 2명 이상 포기/시간 초과했으면 입력 문제, 규칙 오해, 경로 난이도를 notes로 구분한다. 시간 부족으로 시작하지 않은 수로는 이 기준에 넣지 않는다.
- 재미/다시 할 의향이 낮고 입력·규칙 문제는 없으면 반복 플레이의 동기를 재검토한다. 별 기준은 무조건 낮추지 않고 수집 목표로 진행한 lab 기록을 먼저 확인한다.
- 수정 후 같은 과제를 새 초보에게 시험한다. 같은 참가자의 향상은 학습 효과가 섞이므로 개선 효과로 단정하지 않는다.

보고서는 “관찰 → 재현 가능한 원인 → 최소 수정 → 재시험 결과” 순서로 갱신한다. 휴대폰 결과가 없는 상태에서 물리 기기 조작 품질이나 출시 준비 완료를 선언하지 않는다.

## 현재 완료 범위

시험 절차·빈 기록 양식·분석 도구·격리된 테스트 빌드를 준비했다. 자동 검증과 브라우저 기능 확인은 별도 개발 검증이며 실제 이용자 파일럿을 대신하지 않는다. **다음 단계는 5명의 실제 코어 세션과 후반 세션을 진행해 결과를 입력하고 분석하는 일이다.**

이번 개발 검증에서는 자동 테스트 30개와 전체 48개 수로 검증을 통과했다. 분석 도구의 예제는 단위 테스트 안의 가상 데이터이며 결과 보고서에 포함하지 않았다. 360×640 브라우저에서 기본 모드의 48번 잠김, lab 모드의 48번 진입·장치 안내, QA01의 코어 1회 진행 유지, QA02 새 기록, 같은 서버의 정식 빌드가 테스트 진행을 읽지 않는 것을 확인했다. Excel 양식은 모든 시트의 레이아웃과 빈 입력/수식 상태를 검사했다. 물리 휴대폰과 실제 이용자 시험은 미실시다.
